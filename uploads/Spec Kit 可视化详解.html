官方方法论（spec-driven.md）的原话：“Specifications don't serve code — code serves specifications.” 维护软件从此意味着演进规格；调试意味着修正生成了错误代码的那份规格与计划；需求变更不再是打乱计划的意外，而是走一遍「改规格 → 重新生成」的正常流程。

01 · 核心理念

六条原则：为什么规格能「驱动」开发

SDD 不是「先写文档再写代码」的瀑布复辟。它成立的前提是：AI 已经能把足够精确的自然语言规格可靠地翻译成代码，缺的只是结构。Spec Kit 提供的正是这套结构。

P1

规格即通用语

规格是首要产物，代码只是它在某个语言/框架下的一次表达。团队评审、版本管理、分支合并的对象首先是规格。

P2

规格可执行

规格必须精确、完整、无歧义到能直接生成可运行的系统——意图与实现之间不留「靠默会」的缝隙。

P3

持续校验

一致性检查不是一次性关卡：AI 持续地在规格里找歧义、矛盾与缺口（clarify / checklist / analyze 三道工序）。

P4

研究驱动上下文

规划阶段先做技术调研（research.md）：库的兼容性、性能、组织既有约束，先查清再决策，每个选型都留依据。

P5

双向反馈

生产现实反哺规格：性能瓶颈变成新的非功能需求，安全漏洞变成约束所有后续生成的规则。

P6

分支探索

同一份规格可以生成多套实现，分别优化性能、可维护性、体验或成本——规格稳定，实现可换。

02 · 主流水线

SDD 九步流水线（点任意一步看详解）

宪法只建一次，其余八步每个功能重复一遍。所有命令都在 AI 助手的对话里逐个运行、逐步评审，而不是在终端里——每一步的产物都是一份 Markdown 文件，落在功能目录里供下一步读取。

核心步骤 质量工序（强烈建议） 收敛循环 命令拼写随助手而异：Copilot / Claude 多为 /speckit-xxx，Codex 为 $speckit-xxx，旧版为 /speckit.xxx
🔁 收敛循环：implement 之后运行 converge，它把代码库现状与规格/计划/任务逐项比对，把未完成、未覆盖的部分追加成新的收敛任务；重复 implement → converge，直到 converge 报告 Converged 才算真正完工。
03 · 上手

三步装好：CLI、初始化、打开助手

前提：Python 3.11+、uv、一个受支持的 AI 编程助手，Linux / macOS / Windows 均可。

1

安装 Specify CLI

uv tool install specify-cli 全局安装；也可用 specify self check / upgrade 自检与升级。

2

初始化项目

specify init 项目名 --integration <助手> 生成 .specify/ 骨架，并按所选助手落好命令文件；已有项目可原地初始化。

3

在助手里跑流水线

在项目目录启动你的编程助手，之后所有 /speckit-* 命令都在助手对话中逐个执行、逐个评审。

# 终端里：安装并建项目（示例用 GitHub Copilot）
$ uv tool install specify-cli
$ specify init my-project --integration copilot
$ cd my-project

# 然后启动你的 AI 助手，在它的对话里逐个运行（示例为 Copilot 的 skills 语法）
/speckit-constitution  Create principles focused on code quality, testing, and maintainability.
/speckit-specify       Build a photo organizer with albums grouped by date and a tile preview of each album.
/speckit-plan          Use Vite with vanilla JavaScript. Keep images local and store metadata in SQLite.
/speckit-tasks
/speckit-implement
/speckit-converge
04 · 产物目录

所有产物都是仓库里的 Markdown（点文件看说明）

没有数据库、没有云端服务：项目级资产在 .specify/，每个功能的全部文档在 specs/<编号-功能名>/ 一个目录里，跟着 Git 分支一起评审、合并、演进。

my-project/
.specify/ ← 项目级骨架
specs/ ← 每个功能一个目录
001-photo-organizer/
.specify/bugs/ ← 修 Bug 流程的报告
.specify/assessments/ ← 想法评估的卷宗

解剖一份 spec.md：它只回答「做什么、为什么」

规格模板有一条硬约束：只写 WHAT 和 WHY，禁止写 HOW——不许出现技术栈、API、代码结构。这样规格在实现技术变化时依然稳定。含糊处不许猜，必须打上 [NEEDS CLARIFICATION: 具体问题] 标记留给 clarify 工序处理。

用户故事User Stories · P1/P2/P3

按优先级排序、各自可独立交付与测试的故事，每个故事带 Given / When / Then 验收场景——先做完 P1 就是一个能用的 MVP。

功能需求FR-001 …

编号化的功能需求清单（如「系统必须允许用户按日期自动分组照片」），后续 plan、tasks、测试都引用这些编号做追溯。

成功标准Success Criteria

可度量、与技术无关的结果指标（如「用户在 3 次点击内打开任意相册」），用来判断功能到底算不算做成。

边界与假设Edge Cases / Assumptions

边界情况、关键实体（相册、照片、标签……只定义概念不定义表结构）和显式写下的假设，防止 AI 私自脑补。

05 · 实走一遍

案例：官方用「实时聊天」演示的生成链

方法论文档给出的对照很直观：传统方式光文档工作约 12 小时；SDD 三条命令约 15 分钟产出同等齐全的文档集——省下的不是打字时间，而是「不遗漏、可追溯」。

第 1 步 /speckit-specify —— 一句话变规格（约 5 分钟）

命令自动完成三件事：扫描已有 specs 定下新编号、按语义生成并创建分支、套用模板生成结构化规格。

/speckit-specify Real-time chat system with message history and user presence
# → 创建分支 003-chat-system
# → 生成 specs/003-chat-system/spec.md（用户故事 + 验收标准）

第 2 步 /speckit-plan —— 规格变技术计划（约 5 分钟）

给出技术取向后，计划连同调研、数据模型、接口契约、验证脚本一并生成，每个技术选择都回链到具体需求。

/speckit-plan WebSocket for real-time messaging, PostgreSQL for history, Redis for presence
# → plan.md / research.md（WebSocket 库对比）
# → data-model.md（Message、User 模型）/ contracts/（WS 事件 + REST 端点）
# → quickstart.md（关键验证场景）

第 3 步 /speckit-tasks + /speckit-implement —— 计划变任务、任务变代码

tasks 按阶段与用户故事组织、标好并行与依赖；implement 按序执行，写完再用 converge 对照规格验收，直到报告 Converged。

/speckit-tasks        # → tasks.md（T001…，[P] = 可并行）
/speckit-implement    # → 按 tasks.md 逐条落地代码与测试
/speckit-converge     # → 比对代码与规格，未覆盖项追加为新任务，循环至 Converged

传统做法（同一功能）

  1. 写 PRD 文档 2–3 小时
  2. 写设计文档 2–3 小时
  3. 手动搭项目结构 30 分钟
  4. 写技术规格 3–4 小时
  5. 写测试计划 2 小时
合计 ≈ 12 小时，且文档与代码从此各走各路

SDD 做法

  • 三条命令 ≈ 15 分钟生成同等文档集
  • 模板保证非功能需求、异常处理不被遗忘
  • 每项技术决策可回溯到需求编号
  • 文档即代码的生成源，天然保持同步
重点不在快，而在全与可追溯
06 · 三条流程线

不止做新功能：修 Bug 与评估想法是两条独立线

README 把入口讲得很清楚：三条线是互相独立的入口，不是必经的阶段。SDD 在核心包内；修 Bug 与想法评估是捆绑扩展，用到时在终端装上即可，都不要求先跑过 SDD。下面每条线的每个节点都可以点开，看它发生在什么场景、谁参与、具体干什么。

目标产物：一个被完整带过规划、实现与收敛的功能

宪法建一次；每个功能重复「规格 → 计划 → 任务 → 实现 → 收敛」，质量工序（clarify / checklist / analyze）穿插其中。全部产物在 specs/<编号-功能名>/。

终态：Converged（代码与规格完全对齐）

目标产物：定过性的原因、有边界的修复、留档的验证

先在终端装扩展：specify extension add bug。然后在助手对话里依次跑三步，报告落在 .specify/bugs/<slug>/。关键纪律：只有 verdict = verified 才算真修好，partial 与 failed 都要如实记录。

/speckit-bug-assess "Submitting an empty password crashes the login form." slug=login-crash
/speckit-bug-fix    slug=login-crash
/speckit-bug-test   slug=login-crash
verified ✓ 修好partial 部分缓解failed 未修复

目标产物：一个有证据支撑的 go / 澄清 / 砍掉 决策

先在终端装扩展：specify extension add assess。不需要任何源代码，也不需要先有 SDD 功能流程。卷宗落在 .specify/assessments/<slug>/；遇到未知项，官方建议直接改 Markdown 卷宗（自己改或让助手改），而不是整阶段重跑。

/speckit-assess-intake   "Let users work offline and sync when they reconnect." slug=offline-mode
/speckit-assess-research slug=offline-mode
/speckit-assess-define   slug=offline-mode
/speckit-assess-shape    slug=offline-mode
/speckit-assess-decide   slug=offline-mode
go → 把 decision.md 交接给 /speckit-specify 开工needs-clarification 先澄清kill 砍掉（留档的「不做」也是有效成果）
07 · 宪法

宪法：写进仓库的「项目基本法」

/speckit-constitution 生成的 .specify/memory/constitution.md 是全项目最高约束：之后每条 speckit 命令都会引用它做决策与检查。它保证今天和明年、换哪个模型生成的代码，架构品味一致。官方示例宪法有九条，其中四、五、六条故意留白给各项目自填。

ARTICLE I

库优先

每个功能必须先做成独立的库，禁止直接把功能写进应用代码——从源头逼出模块化与清晰边界。

ARTICLE II

CLI 接口强制

每个库必须经命令行暴露能力：文本进（stdin/参数/文件）、文本出（stdout），并支持 JSON——一切功能可观察、可测试。

ARTICLE III

测试先行（不可协商）

测试先于实现：先写测试、经用户批准、确认测试失败（Red），才允许写实现代码。

ARTICLE IV–VI

项目自定治理

留给各项目填写本组织的不可协商项：如集成测试要求、可观测性、版本与破坏性变更、安全边界等；analyze 会照单检查。

ARTICLE VII

简单优先

初始至多 3 个项目；不为假想的未来需求预留结构。多出的复杂度必须在计划里书面说明理由。

ARTICLE VIII

反抽象

直接用框架本身，不要再包一层；同一概念只保留一份模型表示。抽象必须挣得它的存在资格。

ARTICLE IX

集成优先测试

测试用真实环境：真数据库优于 mock、真实服务优于 stub；契约测试在实现之前强制完成。

ENFORCEMENT

Phase -1 门禁

plan 模板把这些条文变成开工前门禁清单：简单门、反抽象门、集成优先门逐项打勾；过不了就把例外理由写进「复杂度追踪」留痕。

AMENDMENT

修宪程序

原则稳定但可演进：修改须写明理由、经维护者评审、评估向后兼容——宪法文件自身带日期化的修订记录。

模板如何「管教」大模型

Spec Kit 的真正机关在模板里：模板本质是精心设计的约束提示，把 LLM 从「创意写作」收束成「规格工程师」。官方总结了七种约束手法，最关键的四种是：

a

禁止过早落实现

规格模板明示 ✅ 只写用户需要什么与为什么，❌ 不写技术栈/API/代码结构——逼模型保持抽象层级，规格不因技术选型变化而失效。

b

强制暴露不确定性

含糊处必须打 [NEEDS CLARIFICATION] 标记而不是猜。比如「登录系统」没说认证方式，就得标明待澄清，杜绝看似合理实则错误的假设。

c

清单即「英文的单元测试」

模板内置完整性清单（无待澄清标记、需求可测、成功标准可度量……），模型交付前必须自查一遍，相当于给规格本身写了测试。

d

测试先行的文件顺序

实现模板规定创建顺序：先 contracts/，再按契约→集成→端到端→单元的顺序写测试，最后才写让测试通过的源码。

08 · 扩展生态

六个可组合的扩展机制 + 助手集成层

官方的定制哲学是「从满足需求的最小改动开始」：改一个模板、加一条命令、挂一个钩子，都不必推翻整条流水线。各机制都可通过 Catalog 发现与安装，也支持企业私有目录与离线使用。

INTEGRATION集成

把 Spec Kit 接到某个 AI 编程助手上（或在助手间切换）：specify init --integration <key> 按助手落好命令/技能文件与目录约定。

EXTENSION扩展

增加一条命令、一个质量门或一整条流程（如 bug、assess），还能连外部工具与服务；支持在 speckit 命令前后挂钩子、响应助手生命周期事件。specify extension add bug

PRESET预设

整体调整模板、命令、术语或方法论，也用来落地组织或监管标准（如要求计划中全程可追溯）。单个项目的临时改模板，用项目级本地覆盖即可。

WORKFLOW工作流

把提示词、命令、质量门与 shell 任务编排成自动化管线；可用 overlay 修改已装工作流而不必 fork 它，也能自加可复用的工作流步骤。

BUNDLE捆绑包

把某个角色或团队的一整套配置——扩展 + 预设 + 工作流 + 步骤——打包成一键安装的 curated 套装。

CATALOG目录

组件的发现与分发：官方带社区目录，组织可自建私有目录并做鉴权。用 specify extension search、preset search、workflow search、bundle search 检索当前目录。官方提醒：目录收录不等于审计或背书，装社区组件前先审源码。

支持的 AI 编程助手（部分）

集成是可插拔的：同一套规格产物，谁来当「执行者」可以换。各助手的调用拼写不同——这也是为什么命令在不同助手里长得不一样。

09 · 评价

优点、代价与适用边界

基于官方文档与方法论的实读判断：Spec Kit 解决的是「AI 写代码失控」而非「AI 不会写代码」——它的全部设计都在给模型的自由度套上可评审的结构。

✓ 优点

  • 意图不再丢失：需求、决策、任务、代码同仓同分支、编号互链，三个月后仍能回答「这行为什么是这样」。
  • 评审点前移：在规格和计划阶段评审（便宜、可读、非技术成员也能参与），而不是等代码写完才发现方向错了。
  • 约束即质量：模板用 [NEEDS CLARIFICATION]、完整性清单、宪法门禁把「别猜、别过度设计、先写测试」变成流程强制项。
  • 不绑助手与模型：产物是纯 Markdown，集成层可换；换模型、换 CLI 不动规格资产。
  • 变更友好：需求变更走「改规格 → 重出计划/任务」的正道，而不是在代码里层层打补丁。
  • 生态可长大：扩展/预设/工作流/捆绑包四层组合，个人玩法与企业合规（私有目录、离线、鉴权）共用一套机制。

✕ 代价与局限

  • 流程重量真实存在：九步流水线每步都要调模型、等评审；改文案、修小样式这类小事走全程是净亏，官方也承认三条线按需取用。
  • 成本随步数走：长规格多轮 clarify/analyze/converge 的 token 与时间开销可观，且工具本身没有内置的成本控制面。
  • 上限取决于模型：它只负责编排与约束，规格与代码质量仍由背后的助手和模型决定；弱模型会产出形式齐全但内容空洞的文档。
  • 规格会腐烂：implement 后手改代码而不回写规格，真相源头就名存实亡——converge 能查偏离，但执行纪律仍在人。
  • 项目仍年轻且迭代快：2025-08 才建仓、已发 234 个版本，命令形态仍在演进（如 taskstoissues 已被标记弃用、迁移到 github 扩展），跟随成本不低。
  • 格式约定有学习成本：用户故事优先级、验收场景、编号追溯都有固定写法，团队不按约写，后续工序的收益会打折。
场景建议
新功能 / 新模块，多人协作、要长期维护全程 SDD。规格评审 + 编号追溯的收益在这里最大。
接手陌生代码、需求本身模糊先 clarify 再 plan。把不确定性在写代码前花掉，是这套工具最值钱的部分。
