# Feature Specification: 审批通知提醒器

**Feature Branch**: `005-approval-notifier`

**Created**: 2026-10-21

**Status**: Withdrawn（2026-10-21 随 e05b70c 整栈移除，规格仅留档）

**Input**: User description: "设计一个通知提醒器，弹出审批事项"（负责人在看板 T-020 卡片语境下提出，并选定「立成规格 + 任务卡」；提醒分级与弹窗形态以负责人已确认的交互原型为准）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 审批请求不漏看 (Priority: P1)

负责人把任务派给 agent 后就去做别的事（切到其他板块、其他应用，甚至把窗口最小化）。某个会话里的 agent 触发审批请求（跑命令、改文件等）停下来等待时，提醒器立刻在应用内弹窗，并在窗口不在前台时同时发出系统通知。弹窗完整展示审批内容，负责人点「查看」即跳到对应会话的审批卡；也可以在弹窗内直接批准或拒绝。批完弹窗自动消失，agent 继续工作。

**Why this priority**: 审批是当前协作里唯一「人不点就全线停摆」的环节。现状只有会话内的审批卡，不主动找人——负责人不盯着那个会话就不知道 agent 在干等，派发的并行收益被等待吃掉。这条故事是本功能存在的理由。

**Independent Test**: 在一个会话中触发一次命令审批后立刻切到看板板块并最小化窗口，验证系统通知出现；点击通知，验证窗口被唤起、切到该会话且审批卡被定位高亮；再触发一次审批，在弹窗内直接批准，验证 agent 继续执行且弹窗消失。

**Acceptance Scenarios**:

1. **Given** 某会话产生待批准的审批请求，**When** 负责人在其他板块浏览，**Then** 应用内弹出该审批提醒，内容含审批种类、所属会话与完整待批内容
2. **Given** 审批请求产生时应用窗口不在前台（失焦或最小化），**When** 事件发生，**Then** 除应用内弹窗外还发出一条系统通知
3. **Given** 负责人点击系统通知或弹窗的「查看」，**When** 跳转发生，**Then** 窗口被带到前台、视图切到对应会话、对应审批卡被滚动定位并高亮
4. **Given** 弹窗已展示完整待批内容，**When** 负责人在弹窗内点击批准或拒绝，**Then** 结果与在会话审批卡上操作完全一致，弹窗随即消失
5. **Given** 同一审批已在会话内被处理（或经弹窗处理），**When** 处理结果生效，**Then** 该审批的弹窗与收件箱条目自动撤下，不需要负责人再关一次
6. **Given** 审批请求产生时负责人恰好正看着该会话且审批卡在可视区，**When** 事件发生，**Then** 不弹窗打扰，仅角标计数增加并高亮审批卡
7. **Given** 一条审批等待超过 3 分钟仍未处理，**When** 超时到达，**Then** 升级提醒一次（再次弹窗 / 系统通知）；此后不再重复升级，只保留角标
8. **Given** 弹窗已被处理或被负责人主动关掉，**When** 负责人事后想复查，**Then** 已决审批在收件箱「历史」页签里可查（结果、时间、会话、内容摘要），未决审批在「待处理」页签里原样保留、agent 仍在等待——弹窗消失不等于事项消失

---

### User Story 2 - 受阻与出错主动报信 (Priority: P2)

agent 干活期间会话出错，或任务卡被判定受阻（blocked）时，提醒器弹一次提醒（会话出错且窗口不在前台时另含系统通知；任务卡受阻不发系统通知），负责人可当场跳过去处理，或点「稍后」把事项挪进待办收件箱——挪走后不再弹窗，但收件箱计数保留，直到事项真正消解。

**Why this priority**: 受阻的卡不会自己恢复，越晚发现浪费越多；但它不像审批那样秒级紧迫，所以只弹一次、可稍后，不升级轰炸。

**Independent Test**: 制造一次会话出错，验证提醒弹一次且不再重复；点「稍后」后验证弹窗消失、收件箱多一条未消解事项；让该会话恢复正常，验证收件箱条目自动消解。

**Acceptance Scenarios**:

1. **Given** 某会话进入出错状态，**When** 状态变化被察觉，**Then** 弹一次 P1 提醒，含会话名与错误摘要首行
2. **Given** 同一出错状态持续存在，**When** 时间流逝或界面刷新，**Then** 不重复弹同一事项
3. **Given** P1 提醒已弹出，**When** 负责人点「稍后」，**Then** 弹窗关闭、事项进入收件箱且保持未消解计数
4. **Given** 事项已进收件箱，**When** 其来源状态恢复（会话不再出错 / 卡片不再受阻），**Then** 条目自动标记消解并移出未消解计数

---

### User Story 3 - 待审查与新 ready 只攒不扰 (Priority: P3)

任务分支进入待审查状态、或新任务卡变为可派发（ready）时，提醒器不弹窗，只把事项记进待办收件箱并更新计数。负责人有空时打开收件箱，按级别一览全部待办：点条目跳到对应卡片 / 分支；对已看过的条目标记已读后计数清零。

**Why this priority**: 这类事项不卡任何人，弹窗只会制造打扰和「狼来了」疲劳；但完全不记又容易漏掉待审查分支。收件箱是「攒着批量处理」的正确形态——派发与审查本来就是负责人批量做的决策。

**Independent Test**: 让一张卡变为 ready，验证无任何弹窗、收件箱新增一条 P3 事项且计数 +1；让一个分支进入待审查，验证收件箱新增 P2 事项（同样不弹窗轰炸，P2 仅应用内轻提示一次）；逐条标记已读后验证计数归零。

**Acceptance Scenarios**:

1. **Given** 一张任务卡由非 ready 变为 ready，**When** 看板状态刷新，**Then** 收件箱新增一条事项，全程无弹窗、无系统通知
2. **Given** 一个任务分支由进行中变为待审查，**When** 看板状态刷新，**Then** 收件箱新增一条事项，并给出一次应用内轻提示（非模态、可忽略）
3. **Given** 同一状态持续存在，**When** 看板多次刷新，**Then** 不产生重复条目
4. **Given** 收件箱有未读事项，**When** 负责人点击条目，**Then** 跳到对应任务卡 / Git 板块并定位，条目可标记已读；全部已读后角标计数归零

---

### Edge Cases

- 同一审批事件被重复投递（重连重放、状态多次推送）时，只许有一个弹窗与一条收件箱条目，以审批 id 去重
- 多条审批同时等待时弹窗按到达顺序排队成栈，互不覆盖，每条独立处理；处理一条不影响其他条
- 审批所属会话在等待期间被删除或回合被停止时，对应弹窗与条目自动撤下，不许负责人点到一个已不存在的审批
- 负责人把某级别的系统通知关掉时，该级别仍须保留应用内呈现与计数；P0 的计数任何设置都关不掉
- Web 预览环境没有系统通知能力：只保留应用内弹窗与收件箱，不报错、不假装已发系统通知
- 应用重启后仍处于待批准的审批，提醒器须能重新呈现（以待批准集合为准重建），不得因重启把等待中的审批弄丢

## Requirements *(mandatory)*

### Functional Requirements

编号约定：本规格 FR 与规格内任务号均用 5xx，与规格号 005 对齐（历史规格的 FR 百号段与任务偏移约定不一致，见 001 的 FR-0xx、002 的 FR-1xx / T1xx、003 的 FR-3xx / T2xx；本规格起统一对齐规格号，避免歧义）。

- **FR-501**: 系统 MUST 把需要负责人处理的事项分为四级并按级提醒：P0 审批请求（应用内弹窗 + 系统通知 + 计数）、P1 受阻 / 出错（弹窗一次 + 计数；其中会话出错另发系统通知，任务卡受阻不发系统通知——受阻为看板派生态、负责人通常正在应用内推进，2026-10-21 负责人裁决 flow-back）、P2 待审查（应用内轻提示一次 + 收件箱）、P3 新 ready（仅收件箱）。除上述通道外 MUST NOT 用弹窗打扰负责人
- **FR-502**: P0 弹窗 MUST 完整展示审批内容：审批种类、所属会话，以及命令原文（含实际 shell）或目标文件路径与改动概要；命令原文 MUST NOT 截断
- **FR-503**: 点击系统通知或弹窗「查看」时，系统 MUST 唤起并聚焦应用窗口、切换到对应会话、滚动定位并高亮对应审批卡
- **FR-504**: 同一审批 MUST 至多产生一个活动弹窗与一条收件箱条目，去重键为审批 id；重复事件投递 MUST NOT 产生重复提醒
- **FR-505**: 审批被任何路径处理（弹窗内、会话审批卡）或其会话结束 / 被删除后，对应弹窗与未消解条目 MUST 自动撤下，无需负责人手动关闭
- **FR-506**: P0 审批等待超过 3 分钟未处理时，系统 MUST 升级提醒一次；升级 MUST 至多一次，之后只保留计数
- **FR-507**: 审批产生时若对应会话正处于当前视图且审批卡在可视区，系统 MUST NOT 弹窗，仅更新计数并高亮审批卡
- **FR-508**: 弹窗内 MUST 提供与会话审批卡等价的批准 / 拒绝操作，且仅在弹窗已完整展示待批内容（FR-502）时可用；系统通知本身 MUST NOT 承载批准 / 拒绝动作，点击通知只执行 FR-503 的跳转
- **FR-509**: 会话出错与任务卡受阻 MUST 各产生一条 P1 事项；同一来源同一状态持续期间 MUST NOT 重复产生；来源状态恢复时条目 MUST 自动消解
- **FR-510**: 看板状态变迁 MUST 被识别并分级：卡片新变为待审查产生 P2 事项，新变为 ready 产生 P3 事项；同一卡片同一目标状态 MUST 只产生一条，状态离开后再次进入可再产生
- **FR-511**: 系统 MUST 提供待办收件箱：汇总全部未消解事项，按级别与时间呈现来源与等待时长，支持点击跳转来源、对 P2 / P3 条目标记已读；未消解计数 MUST 在全局可见处常驻展示，其中 P0 计数 MUST NOT 被任何设置关闭。收件箱入口定版（2026-10-21 负责人定位）：位于左侧图标栏（rail）底部组、主题切换按钮上方的收件箱按钮，角标即未消解计数；点击打开收件箱弹层，含「待处理 / 历史」两个页签
- **FR-512**: 设置 MUST 允许按级别开关系统通知与提醒声音；默认值：系统通知 P0 / P1 开、P2 / P3 关，声音关。关闭某级别系统通知 MUST NOT 影响该级别的应用内呈现与计数
- **FR-513**: 无系统通知能力的运行环境（Web 预览）MUST 降级为仅应用内弹窗与收件箱，且 MUST NOT 报错或宣称已发出系统通知
- **FR-514**: 应用重启后，系统 MUST 以当前待批准集合与看板 / 会话现状重建未消解事项；重启前已标记的「稍后」与已读状态 SHOULD 被保留
- **FR-515**: 收件箱「历史」页签 MUST 记录每条已决审批：决定结果（批准 / 拒绝）、决定时间、所属会话与待批内容摘要；数据来自审批解决事件，应用重启后 SHOULD 从会话持久化记录重建。历史条目只读，MUST NOT 提供撤销或改判已决审批的操作。负责人在弹窗上只关闭未处理时，该审批 MUST 留在「待处理」页签且计数不变（关弹窗 ≠ 消解）
- **FR-516**: 收件箱 MUST 提供第三个页签「进度」（2026-10-21 负责人追加）：逐条呈现全部在途任务卡（状态为 ready / active / review / blocked），每条含任务名、五段进度指示（待派发 → 进行中 → 待审查 → 已合入；受阻以异常态呈现）、执行者、泳道与状态时间戳；数据源 MUST 仅为看板快照，MUST NOT 改动看板状态推导。状态时间戳口径：提醒喂数器亲历的状态变迁按本地时间记录并持久化；未亲历的（应用启动时卡已处于该状态）MUST NOT 编造时间，以 git 合入时间（已合入卡）或「应用打开前已处于此状态」兜底。进度页签 MUST NOT 产生弹窗，MUST NOT 计入未消解计数；点击条目 MUST 跳转看板并定位该卡。本页签呈现的是应用可见的卡片级进度；Muse 协作层内部的细阶段（worker 自验、协调者审查等）不在应用数据源内，不在本条范围

### Key Entities

- **提醒事项**: 一条等负责人处理的事。属性：唯一 id（由来源推导：审批 id，或「来源种类 + 对象 id + 目标状态」）、级别（P0–P3）、来源（审批 / 会话 / 任务卡）、标题与内容摘要、产生时间、状态（活动 / 稍后 / 已消解 / 已读）、跳转目标（会话 + 审批卡，或任务卡 / Git 板块）
- **提醒设置**: 按级别的系统通知开关与声音开关、稍后时长；作用域为本机用户偏好

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 窗口不在前台时产生的审批请求，系统通知在事件后 2 秒内出现的比例为 100%（验收测试样本内）
- **SC-002**: 重复投递同一审批事件产生的重复弹窗数为 0
- **SC-003**: 点击通知 / 弹窗「查看」后落到正确会话与审批卡的成功率为 100%（验收测试样本内）
- **SC-004**: P3 事项产生的弹窗与系统通知数为 0
- **SC-005**: 审批在别处被处理后，其弹窗仍然残留超过 1 秒的次数为 0
- **SC-006**: 负责人从看到 P0 弹窗到完成批准 / 拒绝不超过 2 次点击（弹窗内直批）或 3 次点击（跳转后批）

## Assumptions

- 提醒分级、弹窗形态与「P3 只进收件箱」已由负责人在交互原型上确认（2026-10-21），本规格按此定稿，不再另行澄清
- 弹窗内直接批准 / 拒绝沿用原型设计；其前提是弹窗完整展示待批内容（FR-502），系统通知不带审批动作是刻意的安全边界（防误触批）
- 审批的产生与处理沿用现有机制（契约中的审批请求 / 解决事件与会话待批准状态），本功能不改变审批本身的语义与权限模式映射
- 「待审查」与「ready」「受阻」以看板现有的状态推导口径为准；本功能不引入新的状态定义，看板暂无 CI 结论时不等待 CI 再提醒
- 升级提醒只升级一次、稍后时长默认 10 分钟、声音默认关，均为可配置默认值而非行为边界；其中「稍后」的本期语义为事项消解前不再弹窗，snoozeMinutes 只作偏好落盘、未实现按时长到期重弹（2026-10-21 负责人裁决 flow-back）
- 目标平台为桌面应用（Windows 优先）；Web 预览仅需降级可用（FR-513）
